# B–D：基底、审阅、成品

## 选择基底

从现有已确认简历中选择与目标 JD 最匹配的一份作为基底，只做最小必要修改。基底选择以岗位匹配度为首要依据；匹配程度相近时，优先选所需修改更少的版本，不仅凭更新时间选最新一份。用户已指定基底时沿用其决定。

没有现有简历时，说明缺少基底，先完成可独立进行的岗位分析；用户授权创建首份简历后，按真实材料与明确目标路径起稿。不得把模板或未经确认的草稿当成已确认履历。

**筛选与阅读要求：先按目标 JD、岗位主线和项目内容筛出最相关的 10 份不同版本；不足 10 份时，阅读全部现有相关版本。实际阅读并比较正文、说明实际比较数量后，继续给出基底首选、备选或作出选择，不因数量不足暂停。** 相关性初筛可借助索引、README 和正文检索，但不能仅凭文件名或修改时间挑选，也不能用这些线索代替入选版本的正文阅读。

按真实版本去重：同一版本的 PDF、LaTeX 源码、HTML 预览及导出副本合计一份，仅改文件名或格式不算新版本。推荐时报告去重后的已读版本数，并在现有申请记录中附版本清单、来源路径及相关性入选依据，便于核对。

检索配置中的简历目录时可从近期 14 天开始，但须结合更早版本的岗位和项目线索筛选最相关的 10 份，不把“最新 10 份”当成“最相关 10 份”。相关不同版本不足 10 份时扩大检索；扩大后仍不足，则阅读全部现有相关版本，说明实际比较了几份后继续推荐，不要求用户补齐数量或另行批准降低门槛。辅助命令（用项目选定的解释器替换 python，<skill> 替换为技能绝对目录，<resume-root> 替换为自己的简历目录）：

~~~powershell
python -X utf8 '<skill>/scripts/resume_tools.py' catalog --root '<resume-root>'
~~~

索引仅提供路径、时间、指纹，不判断“已确认”。读候选 README、变更账本及相关用户决定，比较正文的岗位主线、事实准确性、已确认新表述、项目顺序、篇幅和修改成本。

默认不选 stale 历史目录；用户指定旧版则尊重并查陈旧事实。最新 mtime、未确认草稿、最近确认版不能混同。文档与源文件冲突时查实际文件和最近决定；不明冲突列出。

给首选及必要备选，分别链接 PDF/源码，指出可从其他版本吸收的具体条目及来源。D2 展示准确基底路径和拟创建目标路径；选择后锁定，不反复问。

## 改写与 HTML 审阅

先读 JD、当前基底和涉及项目的一手来源，判断现稿哪些值得保留、哪些需要调整。岗位适配主要改变取舍、排序和强调程度，不因换了公司就重写整个能力画像。

### 最小修改与原文复用

按以下优先级完成适配；前面的操作已能清楚体现岗位匹配点时，不再增加改写：

1. **优先保留原文。** 已有表述准确、清楚且适合岗位时直接沿用；尽量不作同义改写，不为润色、统一句式或展示优化而换词。
2. **调整项目顺序。** 按实际贡献与岗位需求调整项目先后，优先展示最相关的证据；只调顺序已足够时，正文不改。
3. **裁剪、拼接已有表述。** 对同一个项目，优先从不同现有已确认简历版本中选取合适的原句或片段，按 JD 所需重点裁剪、组合；注明具体来源，保留原有措辞，只做必要的衔接和去重。拼接后核对事实、指标口径与贡献归属的一致性。
4. **必要时少量改写。** 只有保留、排序、裁剪和拼接仍不足以清楚体现匹配点时，才针对 JD 关键词做最小必要改动；关键词须有一手事实支撑，不为了命中关键词新增未做过的工作。

下文的栏目与质量规则用于判断修改是否必要，不构成全面润色的理由；错误、过期事实和影响理解的重复仍应以最小改动修正。修改理由沿用现有变更记录，说明对应的 JD 匹配收益或具体问题。

### 跨技能交接与结果核对

调用其他技能时遵循入口的[工具与复用](../SKILL.md#工具与复用)范围。great-resume、make-resume 仅由 用户 的显式命令或菜单选择启动，不因本流程进入改写、排版或 PDF 阶段而自动调用。显式调用时交接已有 JD、基底、来源和用户当次要求，按当前上游原始流程执行，不预先缩减其能力或默认交付。

用户要求将显式调用的技能结果纳入当前申请时，对比变化并按当次要求与确认结果处理，不以本流程的默认最小修改原则自动删回原文。沿用现有变更记录、D3 和文件授权，不新增审批节点，也不将未经用户确认的结果自动覆盖到已确认文件。未显式切换技能时，本流程继续按最小修改与原文复用原则执行。

### 按已有栏目组织信息

以当前基底实际存在的栏目为准。以下是常见栏目分工示例；这不是新增栏目清单，不凭通用模板添加“技能”等栏目。

| 栏目 | 要帮助读者形成的理解 | 合适的内容层次 |
|---|---|---|
| 个人亮点 | 最值得记住的优势与整体定位 | 提炼有辨识度的能力组合，必要时配少量最强成果；不拼接项目步骤，不只罗列“全链路”阶段 |
| 研究方向 | 持续研究的问题类别、技术方向及其联系 | 专业而概括的能力版图；具体项目在下方支撑，不在此复述场景、器件、实现路径与验证过程 |
| 项目经历 | 做了什么、个人贡献是什么、为什么有效 | 保留有意义的场景、决策、技术方法与结果，不为了统一“概括风格”删掉技术细节 |
| 教育背景、学术成果 | 学术背景与成果 | 保持事实准确、表达清楚；不为制造改动反复换词 |

### 有力度的概括与取舍

- 仅在现有概括存在具体问题、且复用已有表述仍不能解决时，才从具体工作提炼问题类别、技术方向和可迁移能力；不为每个 JD 重新生成能力画像。允许使用“语音算法”“多模态感知”“端侧 AI”等上位概念，让读者自然理解知识基础、能力延展与研究潜力；不能仅因概念宽于单个项目，就自动收窄、降格为“了解”或补写限定语。
- 一个扎实项目也可以支撑一个研究方向，不要求每项概括有多个项目证明。判断句子是否在表达方向，还是在缩写某个项目。“换掉具体场景或设备后是否仍在表达这个方向”可辅助判断，但不是要求一句话适用于所有项目的硬门槛。
- 概括并非删除专业术语。能帮助定位的方法或问题名称可以保留；只对特定案例有意义的场景条件、模型配置、实施步骤和评测过程优先放项目中。也不把有限动作换成宏大标签来冒充概括。
- 核对明确陈述的职责、已做工作、技术实现、成果数字等事实。方向概括依据整体经历判断，不要求逐词举证，不把合理的积极联想当成错误；但概括不能凭空增加“已完成某项训练/部署”等具体履历。真实缺口按需放在投递分析中，不主动写进简历形成“仅做过……、尚未……”式防御。
- 比较原句与建议前，先指出要解决的具体 JD 表达缺口、事实问题或理解障碍，并优先检索可复用的原句。仅“更有力度”“更顺”“更概括”或“信息密度更高”不足以触发改写；已有原文能解决时不另造同义句。必要修改只处理该问题，可以只调整顺序，也可以不改；不以高亮数量衡量优化成效。

### 先审内容，再做文件检查

在生成 HTML 前审阅建议文案：个人亮点是否提炼优势，研究方向是否保持概括层次，项目是否提供具体支撑，是否存在跨栏目重复或不必要的自我降格。正常内容审阅由助手完成，不新增用户审批节点、逐词审计或独立账本；在现有变更记录中简述必要修改的收益即可。

**项目整体叙述一致性：**将项目标题、职责行、简介和技术条目连起来读，按读者会形成的理解检查信息增量与贡献归属。已明确“独立从 0 到 1”或“负责项目全流程”时，简介主要交代问题与系统价值；删除仅复述下文的数据、训练、评测、部署清单，不再无依据地补写“重点负责某模块”暗示其余工作由别人完成。真实存在的团队分工应保留，技术条目仍需写清具体贡献；不要把这条变成职责禁词表或“所有项目都省略职责”的规则。原文虽符合证据，但确有影响理解的重复、贡献归属歧义或无依据的贡献弱化时，仍应修正；优先删除问题片段或复用其他已确认版本的合适原句，不顺带重写整个项目。

内容质量与文件功能分别报告。证据准确、编辑保存成功、分页正常，均不能替代定位与表达质量的判断。排版遇到篇幅问题先调整布局或提出具体取舍，不借页面密度要求自行扩写或改动已确认文案。

维护写作规则时可用[对照案例](../tests/resume-writing-cases.md)复核概括、保留原文与项目细节三类判断；这些是检查思路的案例，不是所有简历必须套用的文案或额外交付流程。

### HTML 审阅实现

手机审阅模式按[手机审阅](mobile-review.md)选用宿主实际支持的交付方式；多种视图共用当前文案、条目 ID 和版本。呈现方式变化不授权额外改写。

沿用用户基底的 HTML/LaTeX 风格。可读用户已有审阅稿作样式参考，不能把其中事实复制到新用户的简历。没有审阅模板时，根据当前基底创建自包含 HTML，说明不能保证像素一致的部分。不要运行内容和输出位置硬编码的旧生成脚本。

最小审阅功能：
- 完整简历上下文；改写黄、新增绿、顺序蓝；删除内容可从原文对照看到。
- 展开原文、隐藏高亮、直接编辑、保存独立 HTML；原文/来源区不参与编辑。
- 条目有稳定 ID（如 project-a.runtime）；保存后保留 ID、正文、顺序。提示实际保存位置，不假定浏览器下载已写回原文件。
- 来源内容正确转义，当文本处理，不带入网页可执行脚本。
- 保留基底、JD、审阅版本；不预先将建议标 accepted。

复用现有 change-log.json 或 HTML 内嵌 JSON，保留条目原文、建议、理由、证据、pending/accepted/rejected。避免多份账本互相冲突。

交付前实际打开，检查高亮、原文、编辑保存与重开后的保留。工具不可用则披露未验收，不能称视觉检查通过。停在 D3，接受逐条反馈。

## 落实正式简历

1. 核实已有明确编辑授权及目标路径。仅认可建议不自动改文件；一句授权覆盖生成与填表时不重复问。
2. 用户编辑 HTML 或 LaTeX 后先读最新保存稿，提取正文/顺序与上版比较；新编辑优先于旧脚本、旧 HTML 和历史审阅快照。只部分确认则只应用 accepted 项，其余保持基底或继续审阅。
3. 改目标副本，保留基底。**必须在目标简历版本目录下建立或更新 src/ 的 LaTeX 源码**，默认入口 src/resume.tex；正式 PDF 必须由这份同版本源码编译生成。HTML 仅作审阅/预览，不作为正式 PDF 的生成来源。
4. 复用图片/字体/构建脚本；遵循宿主对独立 LaTeX 或多文件项目的编译支持。失败保留源码和诊断，不自行装依赖。
5. 核对成品文字、顺序、指标、日期、论文状态；正确处理 LaTeX 转义，不能用简单字符串比较代替语义核验。逐页渲染检查截断、重叠、孤立标题、链接与页数。页数沿用基底/用户要求，“两页”不是全局硬限制。
6. 若篇幅不足，先提出低优先级删减；实质删改已确认文案须给具体方案，不静默变更。同步预览与账本，记录实际构建文件、验证时间、成品指纹。

## PDF 与 src/ 必须一起交付

- src/ 中必须包含真实、可编辑的简历正文 LaTeX 源码，不能只有空壳、占位文件或整页 PDF/图片嵌入。
- 将编译所需的本地图片、自定义 .cls/.sty、被引用的 .tex 等文件保留在该版本的 src/ 下，尽量使用相对路径；系统 TeX 包、字体和引擎要求在构建说明中注明，不依赖临时目录或其他公司的简历目录。
- **必须交付 `src/build.sh`**，可复制[通用构建脚本](../assets/latex/build.sh)到目标 src/。接口为 `bash build.sh [filename.tex] [output.pdf]`；默认选 resume.tex，否则只有一个 .tex 文件时选它，多个文件要求明确主文件。输出文件名默认 resume.pdf，正式交付时按用户命名要求传入第二参数，输出在 src/ 上级。
- 脚本从自身目录解析路径，用 XeLaTeX 实际编译两遍，失败时保留诊断并不覆盖原有成品。Windows 使用已安装 Git Bash 的实际路径，其他平台使用 Bash；README 记录用户可复现的调用。不得仅交付 .ps1 或说明文字替代 .sh。
- [通用 LaTeX 骨架](../assets/latex/resume.tex)只在缺少合适模板时使用；其中提示文字须全部替换为已确认内容，不把它当完成的简历。使用 TeX 发行版中的 Fandol 字体，不附带私有字体、照片或他人简历。栏目与篇幅服从基底和用户要求，不固定换页。
- 日常编译直接读取用户保存的源码，不依赖历史审阅内容相等检查。确认内容、版本与视觉验收由助手单独完成，不妨碍用户手改后编译。
- 若基底只有 PDF/HTML，须在已授权的目标版本中补齐可编辑 LaTeX 源码并编译核验后才交付正式 PDF，不能省略 src/。编译受阻时保留源码并报告阻塞，不能标记 resume_ready。
- 验证及状态记录同时关联 resume_source 与 final_pdf 的路径和指纹。最终交付同时给出正式 PDF、src/ 主 .tex 文件及构建说明的链接。

## 指纹核验

~~~powershell
python -X utf8 '<skill>/scripts/resume_tools.py' fingerprint '<absolute-source>' '<absolute-review-html>' '<absolute-pdf>'
python -X utf8 '<skill>/scripts/resume_tools.py' verify '<absolute-state-json>'
~~~

将 fingerprint 输出 artifacts 合并到状态，补充 role。仅真实生成/核验新版本后更新指纹，不能为了 verify 通过就重置。哈希相同只证明字节未变，不证明事实和排版正确。变化须按状态参考重新检查。
