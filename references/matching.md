# A：岗位发现与匹配

## 候选集合

1. 明确公司、年份、批次及用户入口；保留内推渠道。读官方 FAQ 中影响本次选择的名额、重复投递、顺序和流程互斥规则。
2. 按分页/筛选遍历；内推链接可能固定集合，通用筛选菜单不一定能扩大范围。必要时与全部职位按职位 ID 比较。
3. 记录总数、读取数、筛选方法、去重键、日期。不完整时披露覆盖，不声称全部遍历。精读候选的完整 JD。
4. 最终详情链接逐个打开，核对岗位、地点及批次；不能拼接未经核实的 URL，也不能仅凭 HTTP 200 认定内容正确。
5. 关闭或读不到的岗位列为待核实，历史 JD 不冒充当期。需要登录时请用户操作，继续分析已可读材料。

## 要求与证据

分出职责、硬门槛、核心能力、加分项。关键要求标记：
- 已匹配：直接可追溯的个人证据。
- 表达缺口：做过，简历没讲清。
- 证据不足：有线索，暂不足以支持结论。
- 真实缺口：明确未做过或不满足。
- 待确认：JD 或个人条件缺决定性信息。

缺材料或读取失败不是能力不足。某项目易读取，不能因此压过尚未核实的研究线；必要时给暂定候选和具体待核实点。

核实方法、职责、结果、个人边界。场景相似、调用现成模型或出现术语，不能自动等同模型创新、统一多模态训练、底层引擎开发。迁移能力可说明，不能写成已做过。

## 排序与交付

先应用生效硬条件，再比较核心职责直接证据、研究/工程深度、量化结果、用户方向偏好、缺口成本及投递机会成本。不输出伪精确匹配百分比，不把学历高等同录用概率高。

所有有事实支持的项目都可独立或组合支撑推荐。证据集中在单项目时说明证明力与局限，不自动排除；无量化指标仍可用可核验定性证据。

默认紧凑表：排名、岗位原名/链接、批次/地点/学历、核心证据、主要缺口、排序理由。补充会影响选择的规则与被排除强候选，不堆满全部结果。

按批次分别推荐只在用户要求时执行。多志愿共用简历则说明共同主线和取舍，不默认每岗能上传独立简历。

保存必要 JD 快照与候选记录，停在 D1。已点名岗位则核实后直接进入 B。

手机审阅模式下，优先把选定岗位的完整 JD 直接渲染在对话中；宿主不支持时按手机审阅参考交付可用替代视图，高亮关键词并保留原句、必需/优先等限定及来源日期；不要只给招聘链接或关键词列表。与简历审阅联动的交付见[手机审阅](mobile-review.md)。
